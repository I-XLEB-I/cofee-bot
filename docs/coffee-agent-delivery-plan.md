# План комплексной доработки Coffee Bot

Обновлено: 2026-09-13. Пользователь разрешил приступить к комплексной работе
после аудита и применить руководство OpenAI к способу работы.

## Итоговая цель

В существующем Telegram-боте пользователь общается обычными словами, получает
ответы по подключённым источникам и может заполнить ревизию несколькими
сообщениями с исправлениями и проверенной записью в действующие таблицы.
Существующие формулы, роли и правила начислений сохраняются. Подготовка Astra
low должна учитывать совместимость, стоимость и доступ API. Возможность
превращения решения в сервис для других сетей оценивается отдельно, без
самовольного изменения источника учёта текущего бизнеса.

## Применённые рекомендации OpenAI

[Using GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model),
прочитано 13.09.2026: продолжать разрешённую работу до проверяемого результата;
задавать только влияющие на результат вопросы; учитывать приоритет инструкций;
проверять конкретные последствия изменения и не повторять достаточные проверки
без причины. Рекомендации сайта не меняют права доступа, модель текущей задачи
или соглашение проекта автоматически. Новые агенты в этой работе не запускались.

Практическое применение: свежая сверка git/production; отдельные ветки; тесты
воспроизводят четыре находки; внешний доступ отключён при регрессионных тестах;
исходные незакоммиченные файлы владельца исключены из коммитов выпуска.

## Этапы и доказательства готовности

1. **Доступ и надёжность AI-моста.** Групповой ответ ограничен до вызова
   источников, бот не публикует owner-ответ; история читается без записи;
   ИИ не держит обработчик Telegram; общий лимит JSON согласован.
   Доказательства: регрессионные сценарии, проверка всего набора, PR,
   последовательное развёртывание backend и бота, состояние production.
2. **Свободный ввод ревизии.** Сохраняемый диалог, обычный русский текст,
   дата/точка/единицы, частичный ввод, исправления и продолжение. Проверенная
   запись через действующие операции, защита от повторов и конфликтов.
   Доказательства: сценарии пользователя от первого сообщения до сверки
   таблиц, перезапуск, повторная доставка и исправление; production-приёмка.
   Вопрос о политике автозаписи задан владельцу 13.09.
3. **Модель и стоимость.** Подготовить совместимое подключение и сравнение
   существующей модели с Astra low; точный учёт всех шагов, лимиты и ошибки.
   Не менять платный провайдер, доступы и лимиты без конкретного выбранного
   варианта. Нужны измерения качества, задержки и стоимости сценариев,
   а не только цены за токен.
4. **Закрытие ограничений данных и функций.** Учёт пополнений после ревизии
   для достоверных закупок, приёмка доставки мониторинга и карта доступных
   действий бота. Каждый выпуск должен иметь собственную проверяемую цель.
5. **Подготовка коммерческого пилота.** Чёткая спецификация изоляции сетей,
   источников, прав, подключения, расходов и поддержки; решение о внедрении
   многоклиентной архитектуры принимается отдельно. Не объявлять готовность
   сервиса на основании готовности внутреннего бота.
